# T3 sessions

Use T3's existing `t3_*` tools. dispatcher returns native tool calls; it does not run another server or copy T3's authentication into the registry. Inside T3, use the injected tools. An outside caller needs the configured T3 MCP connection for the full lifecycle; the installed CLI alone does not expose archiving. Verify the selected environment and project through T3's native project reads. Do not infer project IDs from titles or paths.

A discovery/PM session may use a project for a parent workspace with `workspace_strategy: {"type":"root"}`. As repositories become known, register their existing folders as T3 projects and launch repository-specific executors in new worktrees. The initiative's registry membership spans those T3 projects. Registering a repository is distinct from adopting an existing session.

Example launch specification:

```json
{
  "environment_id": "verified-environment-id",
  "project_id": "verified-repository-project-id",
  "title": "ISSUE-123: Implement cancellation",
  "workspace_strategy": {
    "type": "worktree",
    "baseRef": "origin/main",
    "startFromOrigin": true
  },
  "message": "Use Builder execute. Assignment, authority, acceptance, initiative and registry references..."
}
```

Choose the actual repository base: independent work normally uses its remote default, while dependent changes use the required local base with `startFromOrigin: false`. For an existing checkout, pass `{"type":"existing_worktree","worktreePath":"/absolute/verified/worktree"}`. The thread must be bound through T3 before work starts; shell creation alone does not associate a checkout with its thread. Model and permission choices follow T3 defaults unless the user explicitly selects others; this first interface does not add overrides.

`prepare` supplies a stable `clientRequestId` and prepends the request/member context to the initial message. T3 does not echo the request ID in its launch result. Read the returned thread with `t3_thread_read` (`limit: 1`, `runLimit: 1`, `maxCharsPerItem: 2000`, no cursor) to verify its first user message contains that request context. Save the actual structured launch result with this structured read result in an added `verification` field, then `complete` it. Both reads must name the same thread/project and the message must contain this request's marker. Registry activation confirms membership, not successful execution or delivery. A failed registration after an accepted launch is repaired by completing the same request, never by creating another executor.

`inspect` returns `t3_thread_read`; `message` returns `t3_thread_send` in queue mode. These address the recorded environment and thread. Native sends can change behavior, so only send within the assignment's authority. Use the returned thread link when referring to it in conversation.

If T3 accepted a launch but its reply was lost, `replay-launch --request-id ...` returns the identical stored launch. T3's native `clientRequestId` deduplicates it and recovers the same thread. Do not edit its arguments or send a new request ID. Then perform the normal context verification and complete the original reservation. This explicit recovery is only for pending T3 launches; a lost message reply does not authorize sending the message again.

`retire` returns `t3_thread_organize` with `action: archive`, followed by a verification read. Check no active work, descendants, approvals, or unaccepted obligations remain before archiving. Save the verification read as the completion result: it must name the recorded project/thread and report `archived: true`. An archive acknowledgement alone is insufficient. Worktrees remain; leave automatic cleanup outside this interface.

For explicit adoption, save the actual `t3_thread_read` result with its verified environment ID in a top-level `environment_id` field. Supply the authority and identity evidence. Never adopt a thread just because it appears in the same project, sidebar folder, PR search, or directory.

Verified against T3 v0.1.9: [project/launch tools](https://github.com/pingdotgg/t3code/blob/v0.1.9/apps/server/src/mcp/toolkits/project/tools.ts), [thread tools](https://github.com/pingdotgg/t3code/blob/v0.1.9/apps/server/src/mcp/toolkits/thread/tools.ts), and [outside agents](https://github.com/pingdotgg/t3code/blob/v0.1.9/docs/user/outside-agents.md). Probe installed capabilities before use when the version changes.
